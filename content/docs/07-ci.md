---
title: The check and CI
summary: What fails, what's listed, and how to run it on every pull request.
---
```bash
node ~/github/fraktul/bin/fraktul.ts check docs/arch/model.yaml
```

The check fails when the model points at something that isn't there:

- a file that moved, was renamed or deleted, or isn't tracked by git;
- a function that was renamed or removed;
- a decision record that doesn't exist;
- a `block/inner` box, an `@link` target or an `@expand` block that's gone;
- a tour step whose view, focus box, narration cue or next step is missing;
- an `expect` promise the map no longer keeps.

It also lists files and decision records the model doesn't mention yet. `--strict` fails on those too.

## On pull requests

Check fraktul out next to your project in the workflow and run the check. Repos that aren't checked out on CI are
skipped and named, so the job still verifies everything in the project itself.

```yaml
- uses: actions/checkout@v4
- uses: actions/checkout@v4
  with: { repository: rinsesoft/fraktul, ref: <commit>, path: .fraktul-tool, token: ${{ secrets.FRAKTUL_READ_TOKEN }} }
- uses: actions/setup-node@v4
  with: { node-version: 24 }
- run: npm ci
  working-directory: .fraktul-tool
- run: node .fraktul-tool/bin/fraktul.ts check docs/arch/model.yaml
```

Pin fraktul to a commit and bump it on purpose, so a change in fraktul never surprises a project's CI.

## Publishing

`fraktul build` writes one self-contained page plus narration audio, ready for any static host. `fraktul artifact`
writes the same page without its outer HTML, for hosts that wrap it.
